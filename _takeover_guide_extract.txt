Project Understanding, Milestone Gap Analysis &amp; Developer Takeover Guide
Prepared 31 October 2026  •  Evidence basis: uploaded proposal, architecture brief, Light questionnaire, Full workbook, milestone image, frontend.zip
1. Executive assessment
This is a Responsible AI governance maturity assessment web platform. The Tier 1 MVP supports organization/user onboarding, Light and Full assessments, seven-pillar scoring, maturity results, dashboards, reports and administrative configuration. The GCRAI architecture is a harmonization meta-framework; Tier 2 verification and Tier 3 independent certification are future assurance depths, not interchangeable risk categories.
TAKEOVER STATUS: Partially inspectable. The provided archive contains a substantial Next.js frontend with real API service definitions, but no backend source, database migrations, deployed credentials, test results or client approvals. A page existing in the frontend is not evidence that the corresponding feature works. No production or acceptance claim is justified yet.
2. Product vocabulary &amp; business model
GCRAI: Global Framework for Responsible AI; meta-framework mapping to EU AI Act, NIST AI RMF, ISO/IEC 42001 and OECD principles.
GRAICE: brand/name used by the questionnaire and assessment workbook; obtain client confirmation of product naming and source-of-truth terminology.
Governance loop: Governance → Purpose → Execution → Assurance → Governance.
Seven pillars: Ethical Leadership; Purpose-Driven Innovation; Human-Centric Use; Responsible Implementation; AI Literacy &amp; Workforce Readiness; Data Governance &amp; Integrity; Transparency &amp; Auditability.
Tier 1: Foundational Alignment / self-assessment (MVP). Tier 2: Verified Implementation with evidence/internal verification. Tier 3: Independent Certification / external review (future phases).
Primary roles in proposal: Organization Admin, Assessment User, Platform Admin; Future Auditor reserved. Actual frontend defines SuperAdmin, Admin and Assessor: role alignment requires clarification.
3. End-to-end user journey
Authenticate → identify permitted role and organization
Create/verify organization; invite and manage users
Start Light or Full assessment, select applicable framework version
Load seven pillars and correct questionnaire; save draft responses with progress and resume
Submit assessment; validate completeness and lock or version submission
Backend calculates raw/normalized scores, maturity, pillar findings and recommended actions
Show dashboard, results and historical assessments; generate/download PDF
Admin controls framework content, versioning and auditable changes
Quality assurance, UAT, deployment, monitoring and handover

6. Confirmed discrepancies and investigation priorities
CRITICAL — scoring specification contradiction
Questionnaire labels Q1–4 as Organization &amp; AI Landscape and says scoring begins at Pillar 1 (Q5). Q5–30 = 26 scored items; 26×4 = 104, while docs/proposal show max 120 and maturity bands 0–120. Do not choose a formula unilaterally. Ask client whether first four receive points/weighting or adjust max and bands; add deterministic test fixtures.
CRITICAL — backend unavailable
Frontend APIs reference assessments, frameworks, companies, users, audit logs, webhooks and reporting, but no backend source/schema is in the uploaded frontend archive. Obtain repository, .env.example, migrations, API spec, database sample, and live test environment.
HIGH — dummy OAuth tokens
src/app/(auth)/login/page.tsx contains literal dummy_client_id_token for both Google and Microsoft flows. These buttons must not be represented as production OAuth without real provider integration.
HIGH — multipart upload header
src/services/apiClient.ts sets Content-Type application/json by default; src/services/assessment.service.ts posts FormData to /evidence/upload. Verify and change client to omit Content-Type on FormData so browser sets the multipart boundary.
HIGH — assessment versus assurance scope
Proposal primarily describes Tier 1; frontend includes evidence, findings and auditor mappings. Classify each element as contracted MVP, optional extension or later phase with client approval.
HIGH — naming and role mismatch
Architecture says GCRAI; questionnaire/workbook say GRAICE; package calls itself gcri-frontend. Proposal roles differ from frontend SuperAdmin/Admin/Assessor. Establish canonical naming, permission matrix and organization tenancy boundaries.
MEDIUM — 401 behavior
apiClient clears stored token on HTTP 401 but automatic login redirect is commented out; check UX and route access when sessions expire.
MEDIUM — framework version and report fidelity
Verify that assessment attempts use a frozen framework version and reports reproduce the exact scored question/answer snapshot, thresholds and version in force at submission.
MEDIUM — evidence upload scope/security
Check file type/size rules, authorization, storage keys, download permissions, virus scanning and audit trace; full evidence management may belong to future assurance phases.
7. Scoring rules — pending decision
Questionnaire states answer values Yes/Fully Implemented=4; Partially Implemented=3; Planned/In Progress=2; No/Not Implemented=0; Unsure=0. Preliminary thresholds: Initial 0–30, Emerging 31–60, Established 61–90, Advanced 91–120. These are client-proposed values, not a proven consistent implementation. The proposal assumes 30×4 and 120 max; Q1–4 have special answers and unapproved weighting. Full assessment workbook says 67 questions, but its distinct weighting/threshold details must be confirmed and reconciled separately. Do not apply the Light score scale to Full by assumption.
8. Recommended system design / data ownership
Suggested entities to verify against backend schema (not claims of existing DB tables): Organization, User, Membership/Role, OrganizationVerification, Framework, FrameworkVersion, Pillar, Question, ResponseOption, AssessmentSession, AssessmentAnswer, ScoreSnapshot, Gap, Recommendation, Report, AuditEvent, Notification, EvidenceFile, APIKey/Webhook. Add organizationId to tenancy-scoped data and frameworkVersionId to assessment sessions. Treat server scoring as authoritative; client should present answers, not calculate trusted final results.
